## What it does not resolve

The production `mgxs.h5` is present alongside the archived production statepoint and was compared directly with the regenerated canonical library. In the [MGXS comparison workflow](https://github.com/thenextw4ng/cb-pfr/actions/runs/38100560219), both files had byte SHA-256 `170cc799f496e952465583bb078b2a88eae0f09886a821fd7ee8999d1eb93216`, full semantic SHA-256 `fb4bb5adaaf6ccbc79a364fb37e7e3e1c2a0af9f8955e74d7649143760307d10`, and dataset-content SHA-256 `c054ced2866ce997a617d47c541cc62a25cedd4621bf732a1b9ba44857b14db8`. All 63 datasets, 33 groups, 96 HDF5 objects, and 45 attributes matched exactly.

Therefore production-to-regenerated input identity is now **strongly supported for the pinned upstream canonical model**, including byte-identical MGXS, but the official benchmark gate remains **PARTIALLY RESOLVED / PRIMARY-SPECIFICATION REVIEW REQUIRED**. A separate earlier repeated-smoke artifact recorded a different MGXS byte hash with identical dataset payloads but a one-ULP root energy-boundary difference. The upstream `materials.py` generates group boundaries with `np.logspace(-5, 7, 8)` whenever the builder imports it, explaining how the first boundary can vary by one floating-point step across NumPy builds. The layout-preparation adapter now explicitly normalizes the first and last boundaries to `1.0e-5` and `1.0e7` before MGXS generation. The normalized 18-run repeatability workflow confirms all runs share the production-identical MGXS hash `170cc799f496e952465583bb078b2a88eae0f09886a821fd7ee8999d1eb93216`; see [normalized repeatability evidence](../results/c5g7_repeatability_normalized_2026-10-11/README.md). See `scripts/run_c5g7_layout_study.py` and `results/c5g7_repeatability_smoke_2026-10-11/mgxs_semantic_comparison.json`. This report is input-provenance evidence, not benchmark certification or a reactor-safety claim.
